Multithreaded Process Manager Simulator

A small operating-system “kernel” written in C with POSIX threads. It keeps a shared process table, lets several threads create, terminate, wait for and kill processes at the same time, and uses a monitor thread to record every change safely.

01 Purpose

Real operating systems constantly create and destroy processes while many CPUs touch the same kernel data. This project recreates that problem in a safe, observable way so the core ideas can be studied hands-on.

🧠

Process lifecycle

See how a process is born with fork, becomes a zombie on exit, and is finally reaped by its parent with wait.

🔀

Concurrency

Multiple worker threads run their own scripts in parallel and all modify one shared process table at the same time.

🔐

Synchronization

A pthread_mutex prevents race conditions and a pthread_cond wakes the monitor only when the table actually changes.

📜

Reproducible tests

Behaviour is driven by plain-text script files, so any scenario can be written, replayed and compared with the snapshot log.

Process Control Block (PCB)

Every simulated process is one entry in a fixed array. PID 1 is the init process created at start-up.

typedef struct {
    int pid;           // Process ID
    int ppid;          // Parent PID
    int state;         // RUNNING / BLOCKED / ZOMBIE / DEAD
    int exit_status;   // Exit code
    int children[10];  // Child PIDs
    int child_count;   // Number of children
} PCB;

PCB table[64];
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  monitor_cond = PTHREAD_COND_INITIALIZER;

Components

  • Process manager — the PCB table plus helper functions find(), add_child(), remove_child().
  • Worker threads — one per script file; each reads commands line by line and calls the matching pm_* function.
  • Script interpreter — parses fork, exit, wait, kill, sleep, ps.
  • Monitor thread — sleeps on a condition variable and appends a full table snapshot to snapshots.txt after every change.

Process states

exit / kill →
ZOMBIEfinished, status kept

03 Simulated system calls & script commands

Every function locks the mutex first, edits the table, signals the monitor, then unlocks.

Reading the result

  • Three forks → PIDs 2, 3, 4. PIDs are handed out in order, regardless of which thread asks first.
  • wait 1 -1 returned -1 at t≈200 ms because no child had exited yet — the wait is non-blocking.
  • PID 2 became a ZOMBIE with status 10 at t≈400 ms. Nobody waited for it afterwards, so it stays a zombie — exactly what happens in a real OS when a parent never calls wait().
  • The first two snapshots are identical. Thread 1's fork happened before the monitor wrote its initial snapshot, then the pending change signal produced a second copy. This is a visible example of thread scheduling order.

gcc pm_sim.c -o pm_sim -pthread
3

Run with one script per thread

./pm_sim thread1.txt thread2.txt

The program needs POSIX threads, so on Windows use WSL. The monitor thread runs forever by design, so the program may need Ctrl+C after “All workers finished”.

Design notes & limits

  • Up to 64 processes in total and 10 children per process.
  • PIDs are never reused; DEAD entries stay in the array but are hidden from output.
  • pm_wait() is non-blocking: it returns -1 immediately when no zombie child exists. The BLOCKED state is defined for future use.
  • Ideas for extension: blocking wait, orphan re-parenting to init, PID reuse, a clean monitor shutdown and timestamps in the log.
